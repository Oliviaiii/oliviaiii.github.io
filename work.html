情境

公司過去二十年是「一案一站」：每個客戶網站是獨立專案、各自維護，需求到上線大約 30 天，維護成本隨站數線性成長。團隊用訊息和口頭追需求，沒有統一的 Issue 與發版紀錄；同時要配合 ISO 27001 的文件與稽核要求。

我負責規劃、制度與驗收

  • 定義平台範圍。把各站的客製需求盤點成可設定的功能（版型、Widget、多語系、金流物流、多規格庫存），能用設定解決的就不寫客製；主題樣式改成公版＋客戶覆寫層，客戶可貼自己的 CSS 而不影響其他租戶。
  • 建立交付流程。從訊息追需求改成 GitHub Projects：9 種 Issue 表單、PR 模板、ChangeLog 規範、「階段 × 狀態」雙欄位看板（feature → dev → release → official），每張票在哪一眼可見。
  • 把規格文件化。導入 OpenSpec，累積 104 個能力規格；PR 審查要求規格的每個核取項目對到具體測試。
  • 設計 AI 開發制度。CLAUDE.md 憲章、docs/rules、skills（/issue-start、/commit、/pr-review、/diagnose）、驗收員與對抗審查員 agent、verify-gate hook——讓實作與審查可以大量交給 AI，但「什麼算做完」由制度與證據決定。詳見 AI 工作方式。
  • 自己動手診斷。用 Search Console 分析新舊站索引問題、robots 與 sitemap；量測商品頁 TTFB 1.5–3 秒 vs. 列表 0.4–0.7 秒，找出根因是相關商品無上限查詢＋重複渲染 466 張卡片（748 KB HTML），寫成有數據的 Issue 而不是直接改碼。
  • 親手驗收。用瀏覽器實測每一批票（購物車、物流、金流回呼、會員驗證、多規格編輯），正式站只建可辨識、可回復的測試訂單，卡關的票直接在 Issue 留言寫清楚環境、觀察值與解除條件。

我負責實作並做到落地的功能

  • Widget preview-first 編輯器（#879）：三欄式、預覽優先；資料層、受控樣式參數、畫布與內容編輯；圖片／影片素材在預覽上直接新增、來源逐部各自決定；畫布依語系過濾。
  • 主題 CSS 系統（#694／#695／#722）：主題歸零重寫，在 HTML 零改動下驗證主題可整套切換；首頁 widget 欄寬改由自訂屬性承載，讓主題用同層級選擇器覆寫。
  • 效能與產品修正：編輯器右欄改按需渲染，進頁 HTML 3.03 MB → 1.34 MB（#1138）；完成圖片使用登記補救、公告欄顏色與動畫、物流設定介面、多語系素材與輪播等功能。
  • 文件與規格：77 檔使用手冊（含撰寫指南與同步契約）、OpenSpec 規格與變更提案、ChangeLog 規範。

近期技術與交付演進

  • 驗收開始跨機器、跨環境。把 Windows 與 macOS 的受控憑證、登入與權限回歸納入 issue-qa；遇到環境或帳號問題時，不直接把功能判失敗，而是留下「卡關／待人工驗／待釐清」的可追溯狀態。
  • 晉升不只看程式有沒有合併。測試證據、未驗收範圍與待釐清項目會一起進入發版判斷，避免把 merge 誤當成已驗收、已部署。
  • 部署與帳號安全持續補強。近期也補上 FPM 探測、部署自癒、密碼重設防帳號枚舉與安全稽核紀錄；平台仍維持 Laravel 12／PHP 8.3。

結果

  • 12 個客戶網站整併到同一套平台；需求到上線從約 30 天縮短到 7 天左右；新客戶開站時間少一半以上。
  • 內部回報與客服工單減少約 70%。
  • 需求、Bug、發版全部進 GitHub：六個月內我在這個倉庫開立與驗收的票超過 100 張，PR 審查有紀錄、可追溯。

可以核對的證據

  • 目前使用 shinvo-shop 的正式客戶網站（部分）：璇優品／寅家國際、My Volvo Magazine、TOASTISM、樂盒 La boite、上人文化、Qilumi、徐老師桌球網路商店、三福產業。
  • Issue 表單、PR 模板與 Projects 流程的公開版：issue_tmp（含公開 Projects 範例）。
  • AI 開發制度的結構與原文節錄：制度清單。

情境

供應商在 LINE 裡開賣場、商家在 LINE 裡訂貨。使用者不是工程師，多數在手機上操作：加好友、綁定通知、下單、砍價改單、簽收。任何一步卡住，他們不會回報，只會不用。

我負責產品規劃與驗收

  • 把「第一次使用也走得完」寫成規則。前台禁工程術語、禁 emoji、禁原生 alert／confirm、手機禁橫向捲動、主按鈕樣式統一、清單採「列＋側欄」——80 多條記憶規範，AI 實作時自動遵守，不用每次講。
  • 先驗再發。每個新功能（階梯價、合作邀請、通知中心、簽收流程）先用瀏覽器在本機或測試站實際下單、逐一觸發 LINE 通知檢查 Flex Message、切 5 種螢幕寬度，通過才發版；發版後等 workflow 完成，驗 health endpoint 與實際路徑（例如未登入深連結是否正確導到登入再回到目標對話框）。
  • 把摩擦點變成票。綁定通知流程卡在連動畫面、供應商不知道 rich menu 要貼什麼連結、商家查看賣場 404——我自己操作發現，開票、驗收、結案；能整批處理的就整批派（#139–#162 一次交付）。
  • 教學影片自動化。做了 tutorial-recorder：用腳本操作系統、產生旁白與字幕、重點推近，一行指令產出 mp4 ＋ srt；功能改版重錄也是同一行指令。
  • 上線前清單。舊站轉換的上線前必修清單、網址交換計畫、正式環境唯讀盤點，全部寫成文件進倉庫，讓下一個 session（或下一個人）照著做。

我負責實作並做到落地的功能

  • 從零建立可運作的產品。完成 Docker 環境、Laravel／React 骨架、資料模型、前後台介面與部署流程，不只停在原型。
  • 模組 M1–M14。帳號與身份、供應商賣場與組織、買家與商家成員、合作夥伴關係、訂單（代客建單、配送派工、三種現場簽收）、LINE 通知、LIFF 介面、系統管理後台、商品結構與規格、買家等級與折扣、探索區、公開櫥窗、官方網站、方案與試用期。
  • 該硬的地方。金流回調防護（逾時 throw、鎖內冪等、權威 orderId 與金額）、LINE 憑證健康檢查（供應商一鍵檢查＋每日自動巡檢）、圖片目錄權限與部署清單、LIFF 內對話框限高的真因修正。
  • 發版閘門。Pest、自動型別檢查與 production build 全綠才推；發版後再驗 health endpoint、LIFF 深連結與實際下單路徑。

近期技術演進

  • 執行環境升級。Stage 已升到 PHP 8.5.13，前端工具鏈同步到 Node.js 22；正式線與 Stage 分開確認，不把 release 分支的完成誤寫成正式環境已生效。
  • 部署開始能自我修復。Nginx 安全版本更新後，部署流程會檢查主機設定、PHP-FPM 與 health endpoint；舊 LIFF 網域也納入相容與切換驗證。
  • 跨系統資料正確性。進銷存介接持續補上規格軸順序、token 撤銷與多供應商告警節流，讓問題能被定位到供應商與資料契約，而不是只看到「同步失敗」。

結果

  • 重整 8 個設定分頁與 20 處欄位提示，跨 5 種畫面寬度驗收，檢查 7 條資料深連結並維持租戶隔離。
  • 核心模組 M1–M4、M9–M11 完成，M5／M6／M7 與上線工作進行中；供應商邀請深連結、LIFF 入口修正等已發到測試站並驗證。

情境

接手既有服務：舊功能要穩、新功能要進、每季要向機關簡報、要配合弱點掃描與 App 檢測。其中一項是把節目表資料介接從人工作業改成 CSV 透過雲端儲存自動同步，牽涉機關資訊部門、內部工程師與報價。

我負責規劃、開票與驗收

  • 角色邊界。我負責釐清需求、寫規格、拆票、協調工程與實際驗收；程式實作由工程端完成，不把工程提交算成我的開發成果。
  • 先弄清楚狀況再開會。開會前把所有節目表相關 Issue（含已關閉）盤點成現況摘要；用錄音轉文字整理客戶會議，把口頭需求對回文件。
  • 寫規格與報價。節目表資料介接（CSV）規格說明書 v1.0、報價單與報價異動說明、需求與驗收對照表；把內部監控（Discord 通知）與客戶通知（Email）拆成兩張票，各自驗收。
  • 把測試情境列完整。從一份範本 CSV 產出 37 個測試案例：正常、相容、覆蓋、缺漏、無效、空檔、檔名與邊界，逐案記錄同步結果、前台顯示與通知。
  • 失敗也要看得懂。客戶收到的失敗通知必須說明：哪個檔案、何時、哪裡失敗、既有資料是否變動、下一步做什麼；例外堆疊留在伺服器日誌。
  • 維運自動化。建每日 automation 檢查首頁是否正常、是否出現錯誤殼頁；協調弱點掃描、App 檢測與稽核文件的交付。
  • 可點擊原型。2026 年初做了新版網站與影音後台的可點擊原型（32 頁靜態 HTML，含生活體驗、會員、影音後台四頁 Demo），附前後台 UI／UX 設計理念文件，作為提案與討論的基準。

結果

  • 既有服務維持穩定，新功能持續上線；每季簡報有營運與流量數據可講。
  • 節目表介接從「口頭需求」變成有規格、有報價、有 37 個測試案例的可驗收交付。

我近期負責追蹤與驗收的技術演進

  • 程式碼與部署流程已搬回 GitHub。目前以 GitHub 的 main／develop 為準，部署腳本、Issue 連結與回退分支都已對齊，不再維持兩套來源。
  • 後端升級到 Laravel 13／PHP 8.3。新後端加入 Pest、PHPStan、Rector 與相依安全稽核；我負責確認切換條件、驗收範圍與舊站回退方案。
  • 前端部署改用 Node.js 24。移除未使用的 node-sass、固定間接相依版本；同時追蹤搜尋限速、全文索引、PHP-FPM 與部署不中斷等改善，依 Stage／正式標籤分開驗收。
  • 節目表正式改走 GCS CSV。舊端點停用後，排程監控只檢查實際使用的 iNEWS，避免誤報擋住真正的連線問題。

情境

藥局的系統問題不會在辦公室發生。ERP 升級、健保申報卡住、主機或網路壞掉，都在櫃檯旁邊、病人排隊的時候發生。使用者要的不是解釋，是現在能用。

我做的

  • 每月實地跑近百家藥局：系統導入、教育訓練、健保申報問題；主機、網路、設備故障到現場排除，常帶著備品直接換。
  • 把客戶語言翻成工程問題：哪些是操作、哪些是設定、哪些真的是 bug，回報時附重現步驟。
  • 串接網路商城的自動訂單，把人工轉單改成系統自動跑，訂單處理效率提升約 75%。
  • 之後以外部顧問身分，幫一家藥局系統軟體公司建立專案管理制度、導入 Gitflow，把作業流程整理成符合 ISO 27001 的樣子。

這段為什麼重要

現在我做產品時的直覺——先看使用者卡在哪、驗收要自己走一遍、失敗訊息要讓人知道下一步——都是這段養成的。我不是猜使用者怎麼工作，是真的站在旁邊看過。

情境

我負責從規劃到落地

  • 先寫清楚再動手。Phase 1 SRS、SAD、SDD 與 OpenSpec 變更提案（change-1 骨架與 webhook 閘道、change-2 文件同步、change-3 RAG 問答），每一段照提案交付。
  • 骨架與閘道。FastAPI 服務、LINE webhook 閘道、最小後台（JWT 登入＋RBAC＋audit＋對話檢視＋指標）、DLQ＋告警＋人工重跑。
  • 知識同步與問答。GitHub App 以 Git Trees＋Blobs 只抓 docs/manual 子樹做快照；自架 BGE-M3 embedding（HuggingFace TEI）；FAQ RAG 問答、對話延續、Gemini 自動重試、分類失敗改回「系統忙」。
  • 後台與多租戶。未命中問題回報、後台設定畫面、機密加密、fallback 分類；控制平面 DB、租戶資料模型、每租戶連線 registry、多庫遷移工具、add-tenant runbook。
  • 部署。改用 Hestia＋打 tag 自動部署（不用 Docker），寫正式環境部署交接與「從零把平台跑起來」的伺服器 runbook；清掉多租戶大改留下的文件債。

結果

  • 12 天內從規格到可部署的 Phase 1：RAG 問答、公告推播、未命中回報、多租戶與正式環境部署流程。
  • 整個過程有 SRS／SAD／SDD 與 OpenSpec 對照，接手的人不用讀對話紀錄。

近期技術演進

  • 相依安全更新。FastAPI 已升級以修補參數處理造成的阻斷服務風險，並沿用既有測試與正式部署流程驗證。
  • 知識來源更名也能不中斷。GitHub repository 改名後，文件同步補上轉址相容與來源正名；同步成功、租戶設定與失敗佇列仍分層核對，不因程式合併就宣稱所有租戶都已完成更新。

CASE 06 · AI × 維運

AI 專案風險巡檢

流程設計、查核規則與開票治理 · 現職軟體開發公司

  • 頻率每日巡檢，另由晨間任務彙整真實執行結果
  • 範圍shinvo-shop、LinerpV2、LINE OA Bot、政府 OTT
  • 目的在客戶或團隊先收到外部警訊前，主動辨識需要追蹤的技術與資安風險
  • 邊界只查核、去重、開追蹤票與彙整；不自動修復、部署或通知客戶

我解決的問題

資安公告、套件停止支援、第三方 API 強制更新與重大相容性異動散落在不同來源。等到客戶、供應商或工程師轉貼訊息才處理，容易漏掉「這個專案到底有沒有使用、正式環境跑的是哪一版、修補是否真的已部署」這些關鍵差異。我把查核條件、證據標準與開票門檻寫成固定流程，讓 AI 先做每天都該做、但很容易被忙碌吃掉的第一輪巡檢。

一個風險如何變成可處理的票

  1. 01
    找線索

    讀官方維護者、廠商公告與安全資料庫；一般技術新聞只當入口，不直接當結論。

  2. 02
    核對適用性

    比對 manifest、lockfile、repo commit、部署分支與 runtime；把「程式有用」和「正式站受影響」分開。

  3. 03
    查重與分級

    用專案、元件、CVE／公告別名與根因查既有 Issue；只有新證據才更新，不每天重複留言。

  4. 04
    留下可行動證據

    達到門檻才開票，寫清楚來源、版本、觸發條件、未知事項、緩解方式與建議驗收。

  5. 05
    晨間彙整

    另一個任務只讀真實巡檢結果，區分新票、實質更新、待確認與查核失敗；沒有新票也會回報。

AI 與人的邊界

AI 負責

持續追蹤、交叉比對、找差異、整理證據、依規則去重與建立追蹤。

人負責

決定優先順序、風險接受、正式需求、修補方案、是否部署，以及何時通知客戶。

核心原則：連線失敗不等於零風險、合併不等於已部署、版本字串不等於已確認受影響。AI 可以提早看到訊號，但最後的產品與風險決策仍由人負責。
