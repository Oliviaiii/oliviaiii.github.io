CASE 01 · 0→1

shinvo-shop 建站平台轉型

產品負責人／主導 PM · 現職軟體開發公司

  • 期間2025.06 – 現在
  • 型態多租戶電商建站平台：前台網站＋後台管理＋API，多網域、多語系、多規格
  • 技術Laravel 12 / PHP 8.3、MySQL、GitHub Actions CI/CD、Docker
  • 角色產品負責人，同時實作部分前後台功能；其餘功能由我定義需求、拆票與驗收
平台化
一套後台支援不同品牌站點
產品判斷
區分共用能力與品牌客製需求
規劃＋落地
需求、部分功能實作與跨環境驗收

情境

公司過去二十年是「一案一站」：每個品牌網站都是獨立專案、各自維護，需求到上線大約 30 天，維護成本隨站數線性成長。為了把一次性專案轉成可持續發展的產品，我們設計出一套共用後台與功能模型，前台再透過主題 CSS 與站點覆寫層呈現不同品牌的視覺效果；同一套系統因此能服務不同網站，功能升級與維護不必每站重做。團隊也從訊息與口頭追需求，逐步轉成有統一 Issue、發版紀錄與 ISO 27001 稽核文件的交付流程。

我負責規劃、制度與驗收

  • 定義平台範圍。我會先判斷需求是多個站點都會使用的共用能力，還是只屬於單一品牌的客製需求；適合共用的，再設計成可設定、可重複使用的流程與功能，例如版型、Widget、多語系、金流物流與多規格庫存。品牌視覺則留在主題 CSS 與站點覆寫層，避免客製內容反過來影響平台核心與其他租戶。
  • 建立交付流程。從訊息追需求改成 GitHub Projects：依工作類型設計 Issue 表單、PR 模板、ChangeLog 規範與「階段 × 狀態」雙欄位看板（feature → dev → release → official），每張票在哪一眼可見。
  • 把規格文件化。導入 OpenSpec，持續累積平台能力規格；PR 審查要求規格的每個核取項目對到具體測試。
  • 設計 AI 開發制度。CLAUDE.md 憲章、docs/rules、skills（/issue-start、/commit、/pr-review、/diagnose）、驗收員與對抗審查員 agent、verify-gate hook——讓實作與審查可以大量交給 AI，但「什麼算做完」由制度與證據決定。詳見 AI 工作方式。
  • 自己動手診斷。用 Search Console 分析索引、robots 與 sitemap；實測商品頁與列表的效能差異，定位相關商品無上限查詢與重複渲染，再把觀察值、根因與驗收方式整理成可交付的 Issue。
  • 親手驗收。用瀏覽器實測每一批票（購物車、物流、金流回呼、會員驗證、多規格編輯），正式站只建可辨識、可回復的測試訂單，卡關的票直接在 Issue 留言寫清楚環境、觀察值與解除條件。

近期大型功能規劃

  • 簡訊服務與會員手機驗證。規劃三竹簡訊設定、OTP 手機驗證、國際電話格式、Email／手機登入、既有會員補驗證、發送上限、低餘額與異常提醒、權限和稽核紀錄。除了畫面功能，也先把第三方服務失敗時會員能不能登入、如何恢復，以及哪些資料必須保留等邊界定清楚。
  • 會員點數。規劃從全店規則、點數取得與待生效、效期、折抵順序，到購物車與訂單快照、取消或退貨後的退回／收回、後台人工調整、會員中心餘額與歷程的完整生命週期，讓點數不是單一欄位，而是一套能對帳、可追溯的產品機制。

以上目前屬於需求與規格規劃，與下方已由我實作並落地的功能分開呈現。

我負責實作並做到落地的功能

  • Widget preview-first 編輯器：三欄式、預覽優先；資料層、受控樣式參數、畫布與內容編輯；圖片／影片素材在預覽上直接新增、來源逐部各自決定；畫布依語系過濾。
  • 主題 CSS 系統：主題歸零重寫，在 HTML 零改動下驗證主題可整套切換；首頁 widget 欄寬改由自訂屬性承載，讓主題用同層級選擇器覆寫。
  • 效能與產品修正：編輯器右欄改按需渲染，降低進頁負擔；完成圖片使用登記補救、公告欄顏色與動畫、物流設定介面、多語系素材與輪播等功能。
  • 文件與規格：建立並維護使用手冊、撰寫指南、同步契約、OpenSpec 規格與變更提案，以及 ChangeLog 規範。

近期技術與交付演進

  • 驗收開始跨機器、跨環境。把 Windows 與 macOS 的受控憑證、登入與權限回歸納入 issue-qa；遇到環境或帳號問題時，不直接把功能判失敗，而是留下「卡關／待人工驗／待釐清」的可追溯狀態。
  • 晉升不只看程式有沒有合併。測試證據、未驗收範圍與待釐清項目會一起進入發版判斷，避免把 merge 誤當成已驗收、已部署。
  • 部署與帳號安全持續補強。近期也補上 FPM 探測、部署自癒、密碼重設防帳號枚舉與安全稽核紀錄；平台仍維持 Laravel 12／PHP 8.3。

公開範本與延伸閱讀

  • Issue 表單、PR 模板與 Projects 流程的公開版：issue_tmp（含公開 Projects 範例）。
  • Threads｜從 GitHub 專案管理到 AI 協作開發：
    • Git 與 Repo：先替程式建立可回復的版本紀錄
    • Issue 範本：把需求、範圍與驗收條件寫清楚
    • GitHub Project：集中管理優先度、進度與時程
    • 三軸管理：分開記錄工作、部署環境與驗證狀態
    • Issue 到 Agent：用 PR、測試證據與人工審查接回工作
    • 多工隔離：每張 Issue 使用獨立 branch、worktree、資料庫與預覽網址
  • AI 開發制度的結構與原文節錄：制度清單。

B2B 供貨媒合 SaaS（LINE 生態）

產品重構負責人／AI 協作 Product Builder · 現職軟體開發公司

  • 期間2026.05 – 現在（上線中）
  • 型態媒合供應商與商家的 B2B 供貨平台，提供公開賣場、合作申請與 LINE 叫貨流程
  • 技術PHP 8.5／Laravel 12 ＋ Inertia 3（React 19 / TS）＋ Tailwind 4、PostgreSQL、Pest
  • 重構重新設計共用流程、資料模型與介面；舊系統已完成退役
完整重構
從商業流程、資料結構到前後台介面
領域經驗
把餐飲叫貨現場轉成系統規則
人機協作
我定義與驗收、AI 協作實作、工程師部署

情境

這是一個媒合供應商與商家的 B2B 供貨平台：供應商可以上架商品、經營公開賣場並與既有合作商家交易；商家也能直接在公開賣場尋找合適的供應商、提出合作申請，再透過 LINE 完成日常叫貨。舊系統歷經多人接續修改，許多商業規則、畫面與流程各自寫死，缺少能跨角色共用的設計，修改一個需求常會牽動多條路徑。公司後來把整套系統交由我重新設計與重構，目前舊系統已退役。

我負責重構方向、產品規則與驗收

  • 把餐飲現場經驗轉成產品規則。我做過食材處理、成本控管、供應商叫貨、現場調度與人員管理，熟悉價格變動、臨時加單、到貨簽收與對帳等真實情境；重構時不只搬功能，而是重新判斷供應商與商家各自在什麼時間需要看到什麼資訊。
  • 用自然語言和 AI 協作重構。我把使用情境、資料關係、例外條件、允許與禁止行為寫成規格及驗收條件，讓 AI 依規則實作；每一批變更再由我操作、反駁與修正，不把 AI 產出的程式直接視為完成。
  • 把「第一次使用也走得完」寫成共用規則。前台避免工程術語、原生彈窗與手機橫向捲動，統一主要操作、狀態、清單與錯誤提示；這些規則成為 AI 實作時必須遵守的產品基線。
  • 先驗再發。每個新功能先在本機或測試站實際走過合作申請、下單、改單、簽收與 LINE 通知，並跨手機與桌機寬度驗收；正式部署由工程師執行，我負責交付前條件、切換清單與部署後實際路徑確認。
  • 把摩擦點變成票。綁定通知流程卡在連動畫面、供應商不知道 rich menu 要貼什麼連結、商家查看賣場 404——我自己操作發現，開票、驗收、結案；能整批處理的就整批規劃與交付。
  • 教學影片自動化。做了 tutorial-recorder：用腳本操作系統、產生旁白與字幕、重點推近，一行指令產出 mp4 ＋ srt；功能改版重錄也是同一行指令。觀看實際產出的教學影片。
  • 新舊系統切換。盤點舊版功能與資料、整理上線前必修清單、網址交換與回退計畫；正式環境部署交由工程師處理，我負責確認功能、資料與使用流程能完成交接。

我負責實作並做到落地的功能

  • 從零建立可運作的產品。透過 AI 協作完成 Docker 環境、Laravel／React 骨架、資料模型、前後台介面與測試流程，不只停在原型。
  • 媒合、賣場與合作關係。完成供應商申請與審核、商品與多規格、公開賣場、跨供應商探索、合作邀請與申請、買家等級和折扣，讓商家能先找到供應商，再建立可下單的合作關係。
  • 叫貨到交付。完成購物車、訂單、供應商改單、商家確認、配送派工、現場簽收、退貨、對帳與 LINE 通知，讓線下叫貨習慣有一條可追蹤的數位流程。
  • 該硬的地方。金流回調防護（逾時 throw、鎖內冪等、權威 orderId 與金額）、LINE 憑證健康檢查（供應商一鍵檢查＋每日自動巡檢）、圖片目錄權限與部署清單、LIFF 內對話框限高的真因修正。
  • 交付閘門。Pest、自動型別檢查與 production build 全綠後才交付工程師部署；部署完成再驗 health endpoint、LIFF 深連結與實際下單路徑。

近期技術演進

  • 執行環境升級。Stage 已升到 PHP 8.5.13，前端工具鏈同步到 Node.js 22；正式線與 Stage 分開確認，不把 release 分支的完成誤寫成正式環境已生效。
  • 部署開始能自我修復。Nginx 安全版本更新後，部署流程會檢查主機設定、PHP-FPM 與 health endpoint；舊 LIFF 網域也納入相容與切換驗證。
  • 跨系統資料正確性。進銷存介接持續補上規格軸順序、token 撤銷與多供應商告警節流，讓問題能被定位到供應商與資料契約，而不是只看到「同步失敗」。

CASE 03 · 政府標案

政府 OTT 影音平台

產品／專案經理 · 維運與新功能交付

  • 期間2025.06 – 現在
  • 產品公共影音服務：官網、App、影音內容、新聞、節目表與 CMS
  • 責任需求釐清、規格與報價、跨單位協調、驗收、上線追蹤與季報
  • 技術Laravel 13／PHP 8.5、Vue 2、Node.js 24、Google Cloud Storage、影音與側錄服務
  • 協作機關承辦、資訊部門、內容營運、內部工程與維運
需求到交付
把口頭需求整理成規格、票與驗收基準
跨單位協作
對齊機關、資訊部門、工程與維運
服務不中斷
在既有系統持續運作下導入新功能與改版

情境

這不是從零開始的新產品，而是一套持續對外服務的政府影音平台。官網、App、影音播放、新聞、節目表、會員與後台都在同一個服務鏈上；既有功能不能停，新需求仍要持續交付，還要同時處理資安檢測、稽核文件、季報與跨單位溝通。專案經理不能只轉述需求，必須把每一次變更整理成工程做得出來、機關驗得過、正式環境也能安全切換的交付內容。

代表案例：節目表資料介接重整

原本的節目表依賴既有外部來源與舊流程，這次改成由機關端上傳 CSV 到 Google Cloud Storage，系統自動抓取、檢核並更新前後台。看起來只是「讀一個檔案」，實際上會影響播出日期、跨日節目、腔調與分級顯示、側錄綁定、前台播放連結、失敗通知及既有資料是否被覆蓋；其中有些錯誤不會讓程式中斷，卻會讓播放連結或側錄靜默失效。

我負責把需求變成可交付的系統規則

  • 先拆資料語意，不只抄欄位。逐欄比對機關提供的範例檔、既有資料與前台顯示，釐清舊播出日制與新日曆日制、跨午夜節目、文字編碼、分級、腔調及節目編號的真正用途；把採用、忽略、必填與不在本次範圍的內容寫清楚。
  • 把口頭需求變成規格與報價。整理會議紀錄、規格說明書、需求與驗收對照表、報價及異動說明，再拆成主流程、內部監控、客戶 Email、後台紀錄與前置驗證等可追蹤工作。
  • 先處理「看起來成功」的風險。節目名稱對不到時，匯入可能成功但側錄與播放連結消失；我先要求驗證既有綁定邏輯，改以較穩定的節目編號延續關聯，並用綁定率與資料覆蓋異常主動告警。
  • 內部與機關通知分開設計。內部訊息要讓工程師一眼判斷是否需要處理；寄給機關承辦的信件則必須是繁體中文，說清楚檔案、時間、錯誤位置、資料是否變動及下一步，不直接丟出框架例外或伺服器路徑。
  • 每一條規格都要能驗。我依正常、缺漏、錯誤格式、重複時段、跨月跨年、同檔名覆寫與多檔並存等情境建立測試資料，在測試站走黑箱驗收；發現規格、實作或提示方向不一致時，留下證據、開票並重新驗證。
  • 程式與部署責任清楚分工。我負責需求決策、規格、開票、跨單位確認與實際驗收；工程師負責程式實作及正式部署。我會讀程式與執行紀錄確認無法用畫面驗證的行為，但不把工程提交算成自己的開發成果。

除了新功能，也要照顧正式服務

  • 持續維運與需求管理。處理官網、App、CMS、影音播放與內容營運回報，先判斷是操作、資料、外部服務、既有缺陷或新需求，再安排處理方式與優先度。
  • 資安與稽核交付。協調網站弱點掃描、App 檢測、修正證據與季報內容，讓技術處理結果能轉成機關可查核的文件。
  • 主動發現風險。除首頁健康檢查外，也把停止支援的執行環境與套件風險納入例行巡檢，先建立追蹤項目，再由團隊評估升級與驗收。
  • 原型協助討論。針對新版網站與影音後台製作可點擊原型與 UI／UX 說明，讓提案不只停在文字，利害關係人能直接針對流程與畫面討論。

近期改版中，我負責追蹤與驗收的部分

  • 單一 GitHub 流程。程式碼、Issue 與部署紀錄已統一回到 GitHub，正式、測試與舊版回退分支的用途清楚分開。
  • 後端改版切換。舊後端改為 Laravel 13／PHP 8.5，正式前端與 App 維持相容；我負責確認測試範圍、正式切換條件、已知差異與回退方案，工程師負責改寫與部署。
  • 部署與執行環境更新。前端部署改用 Node.js 24，後端部署改為可回退的版本切換流程；我依測試站與正式標籤確認實際部署版本，不把程式合併當成已上線。
  • 正式環境問題持續回收。搜尋效能、側錄轉檔、排程通知與資料同步等問題，在改版後仍持續觀察；發現異常就轉成可重現、可驗收的追蹤項目。
CASE 04 · 現場

藥局 ERP 與第一線支援

業務工程師（FAE）→ Medira 產品／專案顧問

  • 期間2023.11 – 2024.12（FAE）；2025.10 – 2026.01（遠端顧問）
  • 專案Medira 藥局系統
  • 角色藥局流程與需求釐清、雲端資料與法規風險盤點、專案規劃與開發制度建立
現場 Domain Knowledge
調劑、健保申報、進銷存、設備與網路
雲端新系統
釐清敏感資料、法規、設備串接與備援需求
流程與治理
Gitflow、Repository 權責與 ISO 27001 作業制度

從第一線經驗，走進 Medira 產品規劃

擔任 FAE 時，我服務近百家藥局，從新店建置、系統導入與操作教學，到調劑流程、健保申報、庫存與資料轉移，以及主機、網路和周邊設備串接都實際處理過。後來參與 Medira 藥局系統，一套涵蓋 POS、處方調劑、總部管理與健保申報，並採雲端架構與地端備援的藥局系統。

我在 Medira 負責的部分

  • 釐清藥局實際流程。把調劑、健保申報、進銷存、POS 操作，以及現場主機、網路與周邊設備的使用方式整理成團隊能討論與開發的需求。
  • 釐清雲端資料與法規邊界。Medira 是重新開發的一套新系統，並不是把舊系統直接搬上雲端。由於既有藥局系統的資料庫都在本地端，新系統規劃時需要特別判斷哪些敏感資料適合上雲、應如何符合相關法規與資安要求，以及資料、現場設備、斷線備援和既有操作流程之間要怎麼銜接。
  • 把現場問題轉成專案計畫。依需求相依性、導入風險與驗收條件拆分工作，協助團隊確認先後順序、責任邊界與交付方式；工程師負責程式實作與部署。
  • 重整 Git 與 Repository 治理。原本分支流程不一致，部分 Repository 也放在個人工程師帳號下；我協助把程式資產、權限與協作責任回到組織管理，並建立 Gitflow、審查與發版制度。
  • 讓開發流程能對應 ISO 27001。系統涉及健保與藥局資料，我結合過去參與公司 ISO 27001 導入的經驗，整理權限、變更、審查、版本與紀錄要求，讓專案制度不只方便開發，也能留下可追溯的稽核證據。

這段為什麼重要

我參與 Medira 的價值，是把藥局第一線經驗帶進產品與專案決策：知道調劑人員實際怎麼操作、資料卡在哪裡、設備如何影響流程，也知道規劃新的雲端系統時，哪些風險需要從敏感資料、法規、設備與操作情境一起判斷。這讓需求、開發制度與驗收方式能更貼近真實現場。

CASE 05 · AI PRODUCT

LINE OA AI 客服平台（RAG）

產品規劃、AI 協作開發與落地 · 現職軟體開發公司

  • 期間2026.06 – 現在
  • 產品獨立於 LINERP 的 AI 客服平台，可接上不同產品的 Repository 與 LINE OA；目前以 LINERP @594fgqbs 作為實際範例
  • 角色定義產品規則、規格與驗收；以自然語言和 AI 協作完成實作，並建立部署與維運方式
  • 技術LINE Messaging API、FastAPI、PostgreSQL／pgvector、Redis、GitHub App、地端 DGX 模型服務
Repo 就是知識來源
直接同步產品文件，不另外維護一份客服知識庫
回答有邊界
有依據才回答；資訊不足、系統忙與題外問題分開處理
地端 DGX 模型
改寫、檢索排序與回答生成使用公司內部模型服務

為什麼要做

每個產品原本就會在自己的 Repository 維護操作文件；如果為 AI 客服再複製一份知識庫，功能更新時就要同步改兩邊，也容易讓客服回答落後。我把它設計成獨立產品，直接讀取目標 Repository 的指定文件並建立 RAG 索引，再接到對應的 LINE 官方帳號。LINERP 是目前的實際接入範例，不是這套客服平台本身。

我如何把它做成產品

  • 讓產品文件成為唯一知識來源。以 LINERP 為例，平台直接同步 LINERP Repository 內的操作文件，不需要另外複製或維護客服版文件。文件異動後會重新建立索引並完成檢核，再切換成新版本；同步失敗時保留上一版，避免更新到一半就對外回答。
  • 把「答不出來」設計成正常流程。有文件依據才回答；問法有歧義時先反問，文件沒有答案就留下未命中紀錄，外部服務異常則明確回覆系統忙，不把技術失敗說成產品沒有功能。
  • 使用地端 DGX 完成整套 RAG。問句改寫與答案生成使用 DGX 上的 company-brain，文件向量化使用 BGE-M3，檢索結果再由 reranker 重新排序；平台只把通過門檻的文件片段交給模型組織回覆。
  • 讓 LINE 對話真的能使用。處理 Webhook 驗證、重複訊息、連續傳送與上下文延續，並把回答整理成適合手機閱讀的純文字；失敗工作可重試、可告警，也能由後台查看。
  • 讓獨立產品可以接不同專案。同一套服務可連接不同 Repository 與 LINE 官方帳號，依 LINE 事件辨識 Bot；各 Bot 的知識、對話、設定與金鑰分開管理，資料庫再加上租戶隔離，降低跨客戶讀到資料的風險。
  • 讓非開發者也能維運。後台可以新增 Bot、設定 LINE 與知識來源、查看同步狀態、未命中問題、錯誤診斷、對話與用量；敏感憑證加密保存，重要操作保留稽核紀錄。

我與 AI 的分工

我先寫清楚使用情境、回答邊界、資料隔離、失敗處理與驗收方式，再用自然語言請 AI 分段實作、測試與審查。我會在真實 LINE 對話中驗證問法、追查回答依據，並確認知識同步、後台狀態與部署版本；AI 加快程式產出，我負責決定產品怎麼運作、什麼證據才算完成。

目前能完成的事

  • 直接同步目標 Repository 的產品文件，不需要額外維護另一份客服知識庫。
  • 在 LINE 進行有依據的產品問答、釐清模糊問題並延續同一段對話。
  • 使用地端 DGX 的生成、Embedding 與 Reranker 模型完成問題理解、文件檢索與回答。
  • 以同一套後台管理多個 Bot，查看未命中問題、同步狀態、錯誤診斷及 AI 用量。
  • 透過測試門檻、版本標籤與回退流程部署；Repository 更名或知識來源異動時，也能追蹤同步是否真正完成。

可以直接試用

這套客服平台是獨立產品；目前可加入 LINERP 官方 LINE OA @594fgqbs，把 LINERP 當作實際範例，體驗 Repository 文件同步、RAG 問答與對話延續。

CASE 06 · AI × 維運

AI 專案風險巡檢

流程設計、查核規則與開票治理 · 現職軟體開發公司

  • 頻率每日巡檢，另由晨間任務彙整真實執行結果
  • 範圍shinvo-shop、LinerpV2、LINE OA Bot、政府 OTT
  • 目的在客戶或團隊先收到外部警訊前，主動辨識需要追蹤的技術與資安風險
  • 邊界只查核、去重、開追蹤票與彙整；不自動修復、部署或通知客戶

我解決的問題

資安公告、套件停止支援、第三方 API 強制更新與重大相容性異動散落在不同來源。等到客戶、供應商或工程師轉貼訊息才處理，容易漏掉「這個專案到底有沒有使用、正式環境跑的是哪一版、修補是否真的已部署」這些關鍵差異。我把查核條件、證據標準與開票門檻寫成固定流程，讓 AI 先做每天都該做、但很容易被忙碌吃掉的第一輪巡檢。

一個風險如何變成可處理的票

  1. 01
    找線索

    讀官方維護者、廠商公告與安全資料庫；一般技術新聞只當入口，不直接當結論。

  2. 02
    核對適用性

    比對 manifest、lockfile、repo commit、部署分支與 runtime；把「程式有用」和「正式站受影響」分開。

  3. 03
    查重與分級

    用專案、元件、CVE／公告別名與根因查既有 Issue；只有新證據才更新，不每天重複留言。

  4. 04
    留下可行動證據

    達到門檻才開票，寫清楚來源、版本、觸發條件、未知事項、緩解方式與建議驗收。

  5. 05
    晨間彙整

    另一個任務只讀真實巡檢結果，區分新票、實質更新、待確認與查核失敗；沒有新票也會回報。

AI 與人的邊界

AI 負責

持續追蹤、交叉比對、找差異、整理證據、依規則去重與建立追蹤。

人負責

決定優先順序、風險接受、正式需求、修補方案、是否部署，以及何時通知客戶。

核心原則：連線失敗不等於零風險、合併不等於已部署、版本字串不等於已確認受影響。AI 可以提早看到訊號，但最後的產品與風險決策仍由人負責。
