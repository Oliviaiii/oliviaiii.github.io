A

AI 產品規劃與落地

從問題到上線，不把 Demo 當產品。

Q01

如何管理從需求挖掘、方案設計、研發推進到上線迭代的產品全生命週期？

A｜我會先把業務問題寫成「誰在什麼情境卡住、現在付出什麼成本」，再定義成功指標、非目標與不能出錯的邊界。接著用 PRD／OpenSpec 拆成最小端到端版本，排依賴與風險，讓研發、測試、部署、監控和回滾都在同一張交付地圖上。上線後不以「功能存在」結案，而是用行為與業務數據決定下一輪。

我做過：LINE OA AI 客服先寫 SRS／SAD／SDD，再依 webhook → 文件同步 → RAG → 後台與租戶控制平面分段交付；12 天做到可部署的 Phase 1。

Q02

如何從業務場景找到真正可落地的 AI 機會，而不是為了 AI 做 AI？

A｜我會先畫出現行流程，盤點高頻、耗時、易錯、需要大量查找或判斷的節點，再逐一評估資料是否存在、錯誤能否被發現、能否人工接手、導入成本與可量化收益。若規則引擎或搜尋就能解決，我不會硬上大模型；AI 必須比現況更快、更穩或更省，才進產品池。

我做過：客服要反覆翻手冊回答設定問題，我把它轉成文件同步＋RAG 問答＋未命中回收，而不是只加一個聊天視窗；藥局 ERP 現場則把重複人工訂單改為系統串接，處理效率提升約 75%。

Q03

如何制定中長期路線圖，並落地版本、進度與複盤？

A｜路線圖會以業務成果分成 Now／Next／Later，不以功能清單堆滿季度。每個里程碑都要有 owner、前置依賴、決策期限、驗收條件與可切割的降階方案；日常用看板追「階段 × 狀態」，每次版本結束檢查延誤原因、品質債、使用數據與下一步。

我做過：把團隊從訊息追需求改成 GitHub Projects，建立 9 種 Issue 表單、PR 模板、ChangeLog 與 feature → dev → release → official 的交付階段；B2B SaaS 依 M1–M14 模組推進。

Q04

如何追蹤模型與產業趨勢，判斷商業價值和規模化機會？

A｜我會把新模型放進固定評測：任務成功率、幻覺與拒答、延遲、單次成本、資料治理、供應商鎖定與維運難度。先用公司的 golden set 跑同題比較，再決定要不要替換；趨勢研究的輸出不是新聞摘要，而是「適合哪個場景、預估價值、風險、PoC 門檻與停止條件」。

我做過：AI 客服把生成、embedding、rerank 封裝成 provider，從 Gemini embedding 演進到自架 BGE-M3／vLLM，保留可替換邊界；也實作 token 用量與估算金額，而不是只比較回答看起來像不像。

B

AI 應用設計

先設計失敗路徑，再設計聰明回答。

Q05

如何同時分析使用者需求、業務目標與技術可行性？

A｜我會把同一需求拆成三欄：使用者要完成什麼、公司希望改變哪個指標、技術上有哪些資料／權限／延遲／成本限制。三欄無法同時成立就不進開發；先做資料盤點或 technical spike，把最大不確定性提早驗掉。

我做過：近百家藥局第一線支援讓我習慣從實際操作卡點出發；在 CMS 商品頁效能問題中，我先量測 TTFB 與 466 張重複卡片，再把根因和驗收值寫進 Issue。

Q06

如何設計 Prompt、Agent、企業知識庫與模型呼叫策略？

A｜Prompt 會版本化，明確定義角色、資料邊界、引用規則、不能推論的內容與人工轉接條件；Agent 依最小權限拆工具，每一步保留輸入、輸出與審計，不讓模型直接碰不可逆操作。知識庫要有來源、版本、可見範圍、切塊策略、增量同步與下架機制；模型則依任務的正確率、延遲、成本與敏感度分流。

我做過：RAG 管線包含 GitHub 文件快照、chunking、hybrid retrieval、BGE-M3 embedding／rerank、租戶 Prompt 覆寫、低信心與未命中回報；Agent 工作則用 skills、hooks、驗收員與對抗審查員限制步驟和權限。

Q07

如何把 AI 與既有業務系統深度整合？

A｜我會把 AI 當成業務流程中的一個可觀測元件：透過 API／webhook 接入，先驗證身份、租戶與資料權限，再處理去重、逾時、重試、DLQ、人工接手與稽核。模型失敗時，既有核心流程仍能安全運作，不能讓 AI 變成單點故障。

我做過：LINE webhook 依 destination 找出租戶，資料以 tenant_id＋RLS 隔離；背景工作用 Redis／Arq，失敗進 DLQ 並可人工重跑。B2B 金流回呼則實作逾時、鎖內冪等與權威金額核對。

Q08

如何建立 AI 產品指標，持續複盤與優化？

A｜我會把指標分四層：業務成果（省時、成本、轉換、營收）、使用行為（啟用、任務完成、回訪）、模型品質（正確、相關、拒答、人工接手）、系統品質（延遲、錯誤、token 與單次成本）。先建立導入前 baseline，再用 cohort、問題類型與版本切片，避免平均值掩蓋問題。

我做過：客服後台已記錄真實 token 用量與估算金額、未命中問題、Gemini 429、回答評分與租戶別設定；OTT 則用 37 個案例逐一記錄同步、前台結果與通知，而不是只看 job 成功。

C

跨團隊協作推進

把協作變成人人看得懂的交付狀態。

Q09

如何聯動演算法、前後端、UI 與營運團隊？

A｜我會讓各角色在同一份問題定義上工作，但把介面契約拆清楚：資料輸入輸出、UI 狀態、模型評測、後端錯誤、營運話術與上線責任。會議只處理需要決策的分歧；進度、驗收與阻塞留在 Issue，讓非同步協作也能前進。

我做過：政府 OTT 的 CSV 介接同時涉及機關資訊部門、內部工程師與報價；我先盤點歷史 Issue，再把內部 Discord 監控與客戶 Email 通知拆成不同交付和驗收。

Q10

如何獨立輸出 PRD、流程、原型與迭代文件？

A｜文件會依讀者分層：決策者看一頁問題／價值／風險，研發看 PRD、狀態圖、API 與非功能需求，測試看可執行驗收條件，維運看 runbook、監控與回滾。文件跟版本走，決策改變就同步規格，不讓需求只存在會議和聊天紀錄。

我做過：AI 客服有 SRS／SAD／SDD、OpenSpec changes 與部署清單；OTT 做過 32 頁可點擊原型；CMS 累積 104 個能力規格與 77 檔使用手冊。

Q11

如何協調資源、處理風險並保障節點與品質？

A｜我會先找 critical path，把外部依賴、資料準備、權限、法遵與模型風險放進風險清單；每項都有 owner、觸發條件、替代方案與最晚決策日。遇到卡關不只報紅燈，而是寫清楚觀察值、缺什麼證據、誰能解除與重測條件，讓決策者能立即選擇縮範圍、換方案或調整時程。

我做過：294 張 Issue 中有 293 張留下驗收、決策或卡關留言；正式站驗收若缺權限或樣本，會保留為卡關，不用 CI 綠燈或開發者自述代替證據。

Q12

如何小步快跑、快速驗證、灰階測試並走向規模化？

A｜先選一個高價值、資料可得、錯誤可回復的流程做最小端到端切片；用 feature flag、指定租戶或內部使用者灰階，上線前準備監控、人工接手與 rollback。通過品質與價值門檻後，才把設定、佈建、教材與監控標準化，擴到下一個部門或租戶。

我做過：AI 客服的新租戶先進 provisioning，首次知識同步成功才自動上線；B2B 功能先在本機／測試站實際下單和觸發 LINE 通知，通過後才部署並驗 health endpoint 與真實路徑。

D

企業 AI 效能提升

不是發帳號，而是重做工作流程。

Q13

如何探索研發、營運、行政與業務的 AI 提效場景？

A｜我會先做工作盤點：任務頻率、單次耗時、等待時間、錯誤成本、知識重複度、資料敏感度與人工判斷比例。優先處理「高頻、可驗證、可回復」的工作，再區分成輔助決策、半自動與全自動，不一開始就追求無人化。

我做過：把需求開票、環境建立、PR 審查、瀏覽器驗收、部署檢查與週報整理做成可重複流程；也把教學影片錄製做成一行指令，功能改版可以重錄。

Q14

如何主導 AI 工具引進與自動化工作流程建置？

A｜先用小組試點建立允許資料、權限、成本與人工確認邊界，再把有效做法寫成模板、skill、hook 和 CI gate。工具是否留下，不看使用次數，而看週期縮短、返工下降、品質提升與團隊是否能自行複用；同時保留 audit trail，知道誰讓 AI 做了什麼。

我做過：建立 CLAUDE.md／AGENTS.md、7 個 skills、驗收員與對抗審查員、verify-gate hook、worktree 隔離與 PR review loop；514 個 session 的紀錄可回看工具實際花在哪裡。

Q15

如何量化效率、成本、成長與體驗價值？

A｜每個提效案在開始前就記 baseline：每週件數、處理時間、等待、錯誤／返工、人工成本與滿意度。上線後同口徑比較，另加模型與平台成本，算出淨節省和回收期；若只把時間移到審核或補救，不算提效。

我做過：CMS 平台化後，需求到上線約 30→7 天、內部回報與客服工單約 −70%；藥局訂單串接效率約 +75%。這些是既有案例，新公司會重新建立自己的 baseline，不直接套用。

Q16

如何沉澱方法論，讓成功經驗能被團隊規模化複用？

A｜我會把每次成功與踩坑整理成四種資產：決策原則、可直接套用的模板、可以自動執行的工具、以及帶真實案例的教學。重複出現三次的問題就制度化；每季刪掉失效規則，避免方法論變成只增不減的文件堆。

我做過：把 Issue／PR／發版流程做成公開模板，把常用任務做成 skills，把「沒有驗證不能宣稱完成」做成 hook；77 檔使用手冊、部署 runbook 與 add-tenant 工具讓下一個人不必重讀對話紀錄。
